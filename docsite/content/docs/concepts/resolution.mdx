title: Resolution order
description: How defineEnv merges defaults, config files, and environment variables — and what happens when a required leaf has no value.

---

For every leaf in the schema, `defineEnv` looks in this order. **Later sources win.**

1. **`defaults`** — inline fallbacks passed to `defineEnv({ defaults: … })`.
2. **`config`** — the loaded per-environment object.
3. **Environment variable** — the value pulled from `runtimeEnv` (see [below](#what-runtimeenv-is-for)). On the server that's `process.env`; in the browser it's `window.__env`, hydrated by `<EnvScript />`.

```ts
defineEnv({
  schema: Env,
  defaults: { server: { PORT: 3000 } },  // 1
  config,                                // 2
  // runtimeEnv defaults to process.env or window.__env  // 3
});
```

## What happens when nothing matches

If a leaf is required and has no value from any source, `defineEnv` throws naming the dot-path:

```text
Invalid value at "server.HOST": Invalid input: expected string, received undefined
```

The text after the colon is the validator's own message, here Zod's, so it differs from one validator to another.

Schema-level defaults (`z.string().default(…)`) still apply normally; `defaults` in `defineEnv` is for values you only know at wiring time, not at schema-definition time.

## What `runtimeEnv` is for

By default `runtimeEnv` is `process.env` (server) or `window.__env` (browser, populated by `<EnvScript />` or `readEnv()`). Override it when you need to:

- Inject a fixture in tests.
- Read from a non-default global (e.g. `Deno.env.toObject()`).
- Combine multiple sources before merging.

```ts
defineEnv({ schema: Env, config, runtimeEnv: { ...process.env, ...overrides } });
```

## Type checking of inputs

- `config` and `defaults` are both checked against the **output** type of every leaf (post-coercion): `Config<typeof Env>` and `Defaults<typeof Env>` are the same type, with every key optional.
- That is a compile-time check only. At runtime, `defineEnv` merges defaults, config and environment variables first and then validates the merged object, so a default goes through the leaf's coercion like a value from any other source.

So `db: { URL: 42 }` is a compile error in either one if `URL` is `z.string()`.
